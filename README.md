# 拼豆图纸工坊

上传一张图片，自动转换成拼豆（Perler Beads）图纸：网格图 + 色号 + 用量统计 +
可打印的实物尺寸版，导出 PNG / SVG / PDF。

纯前端，不上传服务器 —— 图片全程在浏览器里处理。

---

## 快速开始

```bash
npm install
npm run dev        # 前端（Vite，5173）
npm run server     # 后端（8787）；不跑也不影响本地功能，只是没有账号/云保存/分享
npm run build      # 类型检查 + 生产构建
npm test           # 跑测试
npm run typecheck  # 前端 + 后端一起做类型检查
```

需要 Node 20+（后端用到内置的 `node:sqlite`，需要 Node 22.5+，推荐 24）。

Windows 上直接双击 `start-site.bat` 会同时拉起前后端（两个窗口，都要开着）。

## 这个工具在解决什么

把图片转成拼豆图纸，粗看很简单：缩小、取色、画格子。但真正决定成品能不能用的，
是几个很容易做错、错了又不容易发现的地方：

- **颜色必须是买得到的**。图像算法随手能生成 3000 种颜色，但拼豆只有固定色号。
  本项目的量化**候选集就是色卡本身**，永远不会产出色卡之外的颜色。
- **边缘不能发脏**。把一个格子里的像素取平均，黑白交界处会得到灰色 ——
  一个原图里根本不存在的颜色，映射到色卡后就是错色。默认改用**主色法**：
  取区域内出现次数最多的颜色，它必然真实存在于原图。
- **打印出来必须是真实尺寸**。图纸是垫在底板下面照着摆的，差一点整张就废了。
- **预览和成品必须是同一个结果**。预览抠掉了背景、导出却还在，
  这种不一致会让用户完全没法信任工具。

下面按这几条展开。

## 内置色卡

9 张，2000+ 个颜色，**全部是真实厂商色号**（MARD、Artkal、Hama、Perler、COCO、
漫漫家、盼盼家、咪小窝）。色号就是用户下单要报的那个号，不是自编的序号。

| 色卡 | 色数 | 色号形式 | 说明 |
|---|---|---|---|
| MARD 221 标准套装 | 221 | `A1`–`M15` | **默认**。国内零售与图纸交流的实际默认体系 |
| MARD 291 全色系 | 291 | `A1`–`ZG8` | 多出 P/Q/R/T/Y/ZG 七十个扩展色 |
| Artkal S（5mm） | 199 | `S01`–`ST6` | 优肯，5mm 规格 |
| Perler（美国） | 103 | `80-19001` | 官方物料号 |
| Hama（丹麦） | 92 | `H01`–`H119` | 社区通行的 H 前缀写法 |
| COCO / 漫漫家 / 盼盼家 / 咪小窝 | 278–291 | `A01` / `A1` / `2` | 国产品牌 |

数据来源、许可以及**来源之间的分歧**记录在 `data-sources/`，由
`scripts/gen-palettes.mjs` 生成到 `src/core/palette/data/`。重新生成是幂等的：

```
node scripts/gen-palettes.mjs
```

几个刻意的取舍：

- **MARD 221 与 291 共用一份基准表**，共用色号的色值必然一致 —— 否则用户会在两张
  色卡上看到同一个 `A1` 颜色不同，无从判断哪个对。
- **默认用 221 而不是 291**：221 是大多数人手里实际持有的套装，用 291 会让自动配色
  产出用户买不到的扩展色号。
- **没有颜色名的品牌（MARD、COCO…）只显示色号**。公开数据源与商家都按「A1 一包」
  销售，`name` 字段就是色号本身；界面靠 `displayName()` 避免渲染成「A1 A1」。
- **色号放不下就退成符号，绝不截断**。Perler 的 `80-19001` 与 `80-19002` 截断后都是
  `80-1`，几十个色号互相无法区分；符号虽然要查图例，但它无歧义。见
  `render/label.ts`。

### 数据流

```
用户选图 → 载入并限制到 1600px（工作图）
              ↓
        [ 参数变化 ] ──→ Worker ──→ ConversionPipeline.run()
              ↑                          ↓
              │              ┌───────────┴───────────┐
              │         预览（900px 小图）      全分辨率量化
              │              ↓                       ↓
              └──────── 画面 / 状态 ←──── pattern（网格 + 色号）
```

### 为什么有 Worker，以及为什么只传一次原图

1600×1600 的 RGBA 缓冲约 10MB。每次调参都重传的话，结构化克隆的开销就超过计算本身。
所以协议分成两条：

- `init` —— 传入工作图，Worker 常驻保存（**只传这一次**）
- `process` —— 只传参数（几百字节），Worker 用保存的图重算

拖动滑块时走的全是 `process`。

每个请求带一个递增 `token`，新请求发出时旧请求立刻作废。否则用户连续拖动会看到
十几个响应依次回放，画面从旧状态一路跳到新状态，而且最后停下的未必是最后一次参数。

### 为什么维护两份工作图

预览**先降采样再调色抠图**，而不是调完再缩。代价从 O(1600²) 降到 O(900²)，
拖滑块时的延迟才跟得上手。降采样保持连通性，背景不会因缩小而断开，所以预览上看不出差别。
**真正决定成品的量化走全分辨率。**

关键约束：预览和全分辨率量化**必须共用同一个背景参考色**。
早期让两边各自自动分析一次，两次结果不一致时用户就会看到
「预览里背景抠掉了、成品里还在」这种没法解释的现象。现在由
`ConversionPipeline.run()` 先解析一次参考色，再喂给两条路径。

## 几个关键决定

### 颜色距离用 CIEDE2000

用 RGB 欧氏距离会把深蓝判成黑色、把深绿判成灰色 —— 因为在 RGB 空间里它们确实很近，
但人眼一看就知道是两种颜色。CIEDE2000 是目前的工业标准，实现见
`core/color/distance.ts`，并对着 Sharma/Wu/Dalal (2005) 的 34 组参考值做了逐项验证。

### 采样默认用主色而不是平均

见上文「边缘不能发脏」。四种模式：

| 模式 | 适用 | 说明 |
|---|---|---|
| `mode` | 卡通、线稿、像素图 | 取区域内出现次数最多的**真实颜色**，边缘锐利 |
| `average` | 照片 | 取均值，但**在线性光空间**累加 —— sRGB 直接平均会系统性偏亮 |
| `median` | 有噪点的图 | 逐通道中位数 |
| `auto` | 不确定时 | 单色占比低于 30% 就认为区域太杂，退回均值 |

### 背景去除：从四条边洪水填充

不是"把所有接近背景色的像素删掉"，而是**从边框出发**向内部蔓延。
区别很实际：白兔子上有白毛，全局删色会把兔子身上也抠出洞，
而从边缘蔓延进不去兔子内部。

### 撤销记的是"改动之前"

每次改动前同步捕获快照，而不是改完再记。滑块有特殊处理：

- `input`（拖动中）→ 只更新参数 + 重算预览，**不进历史**
- `change`（松手）→ 记**一条**历史 + 跑完整量化

撤销点由 `beginLive()` 在拖动第一帧捕获，所以撤销回到的是**拖动之前**的状态。
否则拖一次滑块要按十几次撤销才能回去。

### 打印尺寸

SVG 的 `width`/`height` 直接写成毫米：`总格数 × 豆子尺寸 × 打印倍率`，
浏览器打印时按真实尺寸输出。

**图纸放不下时必须分页**。300 格 × 5 毫米 = 1.5 米，A4 装不下；
浏览器会把过大的 SVG 静默缩到纸宽，于是尺寸悄悄不对了 ——
用户拿尺子一比才发现每格小了一半。所以：

- 按纸张自动算每页格数（5 毫米豆 1.5 倍 → 一页 23 × 34 格）
- 相邻页**重叠 1 行/列**，用户照着重叠的那一行对齐
- 标尺一律用**全图绝对行列号**，每页从 1 重数的话根本不知道接到哪
- 分页的图纸**不加 `max-width: 100%`** —— 宁可溢出（看得见的错），
  也不要静默改尺寸（看不见的错）

### PDF

手写的 PDF 写入器（`core/export/pdf/`），不引第三方库 —— PDF 是纯文本格式，
我们需要的子集（页面树、内容流、标准字体、嵌入 TrueType）并不比已有的 SVG 导出难写。

**两种排版**，导出面板里选：

- **实际尺寸分页**：与打印完全一致（复用 `paginatePattern`），打印出来能垫在底板下照着摆
- **单页全图**：整张图压进一页，页面尺寸随图纸走，适合屏幕上放大看和转发

中文必须自己嵌字体（PDF 内置的 14 个标准字体只有 Latin-1）。字体在**构建期**
用 `scripts/gen-pdf-font.mjs` 子集化到"PDF 里真正会出现的字符"，产出三个共 68 KB 的
TTF，**按需加载**，不进首屏：

| 字体 | 覆盖 | 大小 |
|---|---|---|
| Noto Sans SC | 界面文案 + ASCII + 拉丁字母 + 9 张色卡名 | 54 KB |
| Noto Sans Symbols 2 | 格内标注用的几何符号 | 8 KB |
| Noto Sans Math | 4 个数学运算符（前一个字体不含） | 6 KB |

三个坑值得记下来：

- **字符表不能用空格做分隔符**：空格字符本身就在表里，会被自己的分隔符切碎，
  于是所有空格消失。现在用码点编码。
- **不能让两个字符共用字形**。字体里空格（U+0020）与不换行空格（U+00A0）、
  连字符（U+002D）与软连字符（U+00AD）本来就指向同一字形，而 ToUnicode 一个 GID
  只能映射一个字符 —— 结果是 PDF 里复制出来的空格变成不换行空格、
  `80-19001` 变成 `80‑19001`，搜索和复制全对不上，而屏幕上完全看不出区别。
  现在这类字符直接不进子集，并有测试守着"无字形共用"。
- **所有中文文案必须走同一份模板表**（`fonts.generated.ts` 的 `PDF_LABELS`）。
  在代码里内联一个全角括号，它就不在子集里，PDF 上会印成问号。

**已知限制**：图纸标题是用户任意输入的，而字体子集是构建期定死的，收录不了所有汉字。
标题里有画不出来的字时，页面标题退回默认的「拼豆图纸」，但**文件名与 PDF 元数据
都保留原始标题**（元数据走 UTF-16BE，不受字形限制）。

### 显示与导出共用一份选项

`stores/view.ts` 同时喂给画布和导出面板。用 props 传要穿过整个 App，
而且两边必须是同一份值，否则会出现「屏幕上看着有网格线，导出后没有」。

### 后端只做浏览器做不到的事

图像处理、量化、抠图、PDF **全部留在浏览器里**：原图从不上传，延迟最低，
服务器也不需要买 CPU。后端只负责三件事 —— 身份、存图纸、发分享链接。

技术上是刻意"抠门"的：`node:sqlite`（Node 内置）、`scrypt`（内置）、
`node:http` + 手写路由，**运行时依赖为 0**，部署只要装个 Node。

几个不能省的细节：

- 密码用 **scrypt**（每用户随机盐、`timingSafeEqual`），库里只有哈希
- 会话表只存 **token 的 sha256**，Cookie 是 `HttpOnly + SameSite=Lax`
- 登录失败统一提示"邮箱或密码不正确"，且邮箱不存在时也跑一次 scrypt ——
  否则可以用响应时间枚举已注册邮箱
- 别人的图纸一律返回 **404 而不是 403**，不泄露"存在但不是你的"
- 分享串是 16 字节随机数（base64url），**不用自增 ID**
- 服务端**先卡资源上限再解析**：`parsePatternFile` 会按客户端给的行列分配内存，
  直接信它就是让人随便打内存（行/列 ≤ 300、总格数 ≤ 90000、请求体 ≤ 2MB）

**没有邮件服务，所以不做"邮件找回密码"** —— 那会是一个看起来能用、实际发不出信的功能。
替代品是站长在服务器上执行 `npm run server:reset-password -- <邮箱>`。

## 已知的不足

- **色卡色值是屏幕参考值**，不是厂商公布的 sRGB，与实物有批次色差。真正准确的做法
  是让用户拿色卡实物做一次校准（拍一张已知色号的照片，反推色偏），目前没做。
- **MARD 的公开数据存在多套互相冲突的口径**。本项目采用公开源码库版一套口径、不与
  其他来源混用；与「豆豆工坊核对版」有 10 个色号相差超过 8（最大 38），完整差异见
  `data-sources/mard-differences.md`。
- **COCO / 漫漫 / 盼盼 / 咪小窝 没有材质分类数据**，这些色卡里所有颜色一律按纯色处理，
  没有做推测。其中盼盼和咪小窝的色值序列与 MARD 高度一致（同一份公开数据换了编号），
  数据独立性有限。
- **Perler 表只覆盖实色线**（103 色，特殊色仅 1 个），它的夜光 / 珠光 / 半透明产品线
  没有可靠的开源数据。
- **PDF 汇总页上没有图纸预览缩略图**。参考的商业 PDF 有，需要给写入器加图片
  XObject 支持（约 40 行）；顺带也能解决标题字形的问题。
- **格内标注不压缩长度**。参考 PDF 给每个色号编了一个 3 位短码
  （`80-19001` → `001`），所以它的格子小得多也看得清。我们保持直接用色号，
  长色号的品牌（Perler）在大图上会退成符号、靠图例对照。
- **「我手里有哪些色」只能一个个排除**，没有"照着我的收纳盒建一套色卡"的流程。
  这是社区版最该有的功能之一。
- **长图与超大图**：工作图限制在 1600px 内。更大的图会先缩到这个尺寸，
  细节会损失；有需要的话应该做成按需分块处理。
- **云端一次只编辑一张**：保存是按"当前图纸"整份覆盖/新建，没有历史版本。
- **云端不能重命名**：名字跟着图纸标题走，改标题后需要再保存一次。
- **忘记密码只能找站长**：没有邮件服务，账号找回靠人工重置。
- **没有作品广场**：分享是一对一的链接，没有公开列表、点赞和评论。
- **限流是进程内内存**：重启即清零，多进程部署时需要换成共享存储（单机足够）。

## 部署（以后买服务器时看）

后端只需要 Node，前端仍是纯静态。一个反向代理（Caddy / Nginx）把
`/` 指向前端产物、`/api` 指向 Node 即可，**不涉及 CORS**。

必改的环境变量：

| 变量 | 生产值 | 说明 |
|---|---|---|
| `COOKIE_SECURE` | `1` | 走 HTTPS 时必须开，否则浏览器会拒绝会话 Cookie |
| `ALLOWED_ORIGIN` | `https://你的域名` | 写操作的来源白名单，**不要留 localhost** |
| `TRUST_PROXY` | `1` | 放在反向代理后面时打开，否则限流看到的全是代理 IP |
| `DB_PATH` | 例如 `/var/lib/bead/app.db` | SQLite 文件位置 |
| `PORT` | 例如 `8787` | 只监听本机，由反向代理转发 |

检查单：

- [ ] HTTPS 生效，`COOKIE_SECURE=1`
- [ ] 数据库目录**不在**静态目录里（`data/` 已在 `.gitignore`）
- [ ] 定时备份：`sqlite3 app.db ".backup backup.db"`，连同 WAL 一起拷
- [ ] 进程守护（systemd / pm2），开机自启
- [ ] 日志里不出现密码、Cookie、token
